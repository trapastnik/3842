## HTTP-сервер

**Один общий сервер на порту 8092**, запускается из корня репозитория (главный worktree `main`, **не** из своего worktree):

```bash
cd /Users/dvn/Desktop/WWWWW/BMK/38-42    # ← корень main
python3 -m http.server 8092
```

Запуск из своего worktree вместо main — частая ошибка: сервер тогда увидит только твою feature-ветку, а не общий результат пяти сессий.

Сервер отдаёт всё сразу:
- http://127.0.0.1:8092/ — посадочная со всеми МТК
- http://127.0.0.1:8092/mtkXX-<вариант>/ — конкретный прототип
- http://127.0.0.1:8092/data/ — общие данные

**8092 не трогать никогда** (его lifecycle — только координатор). Если на 8092 чего-то нет — твоя работа ещё не смержена в main, это норма.

**Dev-порт сессии (правило от 2026-07-22, отменяет прежний тотальный запрет вторых серверов):** для проверки НЕзакоммиченной работы сессия МОЖЕТ поднимать временный `python3 -m http.server <свой порт>` из СВОЕГО worktree. Порты закреплены, чужие не занимать:

| Сессия | dev-порт |
|---|---|
| МТК 38 | 8093 |
| МТК 39 | 8096 |
| МТК 40 | 8095 |
| МТК 41 | 8097 |
| МТК 42 | 8098 |
| kiosk-core (платформа) | 8091 |
| координатор (verify) | 8099 |

Правила: поднял → проверил → погасил (не оставлять висеть); в коммиты/доки ссылки только на 8092; 8094 не занимать (совпадает с прод-портом VPS — путаница).

## Координатор

Одна сессия выполняет роль координатора:

- Ведёт корневой `index.html` (сводная страница).
- Ведёт этот `COORDINATION.md`.
- Следит за состоянием HTTP-сервера на 8092.
- Раскладывает по соседним worktree разовые заметки (`SERVER-NOTE.md`, `SYNC-FROM-MAIN.md`) — они не коммитятся, потому что `.claude/` в `.gitignore`.

Координатор **не правит** содержимое чужих МТК. Если меняет общую разметку `index.html` — пишет об этом в «Хронологию слияний» ниже.

Текущий координатор — **`magical-allen-0c3d5f`** (с 2026-05-11).

## Протокол: как сообщать координатору о коммитах

Короткий ответ: **никак специально не сообщай**. Координатор подсасывает информацию через `git log main` и `git diff` после твоего merge — этого достаточно, чтобы понять что появилось.

Что **полезно** сделать дополнительно (минимальная нагрузка на тебя, большая ясность для всех):

1. **Внятное сообщение коммита.** Императив, по-русски или по-английски, упоминай свой МТК: «Add mtk41-grid prototype», «Fix overlap in mtk40-shelf», «Drop mtk42-pendulum, replace with mtk42-archive».
2. **После merge в main — одна строка в «Хронологии слияний»** ниже. Только если изменение не очевидно из имени файла:
   - Удалил вариант / переименовал — пиши.
   - Изменил shared-файл (`data/ne_110m_countries.geojson`, `mtk38-globe/fonts/`, общий CSS) — пиши обязательно.
   - Поменял свой `data/mtkXX.json` — можно не писать.
   - Добавил новый прототип — можно не писать (координатор увидит папку и добавит карточку).
3. **Если хочешь, чтобы координатор поставил карточку прототипа на landing** — это происходит автоматически после merge. Не правь `index.html` сам.

Не нужно писать сводку «что я сделал» в COORDINATION.md после каждого коммита — это шум. Хронология нужна только для **необратимых** или **shared-затрагивающих** событий.

## Контент-политика (изображения / аудио / маленькое видео)

**Решение — вариант A: бинарный контент лежит в git.** Деплой = `git pull` на VPS, никаких дополнительных шагов. Альтернативы (Git LFS, внешнее хранилище / S3) — преждевременная сложность; на нынешних объёмах (десятки МБ на МТК) git справится спокойно.

### Где лежит

В репо **два валидных места** для бинарного контента, оба разрешены через `.gitignore` (`!assets/**` и `!data/images/**`):

```
assets/                        data/
├── mtk38/                     ├── mtk38.json
├── mtk39/                     ├── mtk39.json
├── mtk40/                     ├── images/        ← бинарный контент здесь тоже валиден
├── mtk41/   ← владельцы       │   ├── mtk38/
├── mtk42/      = сессия       │   ├── mtk39/    ← bold-booth: 57 фото из Wikimedia
└── shared/     своего МТК     │   ├── mtk40/
                               │   ├── mtk41/
                               │   └── mtk42/
                               └── mtk42.json
```

**Внутри одного МТК — выбери ОДНО место и держись его.** Не дроби фото между `assets/mtkXX/` и `data/images/mtkXX/` одновременно.

Текущая фактика (на 2026-05-11):
- МТК 39 → `data/images/mtk39/` (bold-booth, ближе к `data/mtk39.json`)
- МТК 41 → `assets/mtk41/` (после миграции из `mtk41-assets/`)
- МТК 42 → `assets/mtk42/portraits/` (после миграции из `mtk42-archive/portraits/`)
- МТК 38, 40 → пока без бинарного контента

Новой сессии: на усмотрение. Если ассеты ↔ JSON-записи (фото объекта из data/mtkXX.json), `data/images/mtkXX/` ближе по структуре. Если ассеты независимые (UI-иконки, видео, скриншоты-постеры), `assets/mtkXX/` чище.

Структура внутри (примеры):

- `<место>/mtkXX/<категория>/<slug>.<ext>` — например `assets/mtk42/portraits/lenin-1924.jpg` или `data/images/mtk39/bsu.jpg`
- `assets/mtkXX/<объект>/<файлы>` — например `assets/mtk41/volgograd-1973-vuchetich/photo.jpg`
- `<место>/mtkXX/manifest.json` или `_index.json` — опционально, если нужен список с метаданными.
- `<место>/mtkXX/tools/` или `_fetch.py` — скрипты подготовки контента (Python и т.п.) тоже в git. `__pycache__/` исключён в `.gitignore`.

`assets/shared/` (кросс-МТК) — менять только через координатора.

### Что разрешено в git

- `png`, `jpg`, `jpeg`, `gif`, `webp` — **только под `assets/` или под `data/images/`**. Глобально в других местах они в `.gitignore` чтобы случайные скриншоты рабочей среды не попадали в репо.

- `mp3`, `ogg`, `wav` — без ограничений (нет глобального бана).
- `mp4`, `webm` — пока без ограничений, но если один файл > 25 MB — посоветуйся с координатором, возможно стоит уйти на отдельное решение (LFS или внешнее хранилище). На сейчас видео нет.

### Размеры

- Цель: суммарно по всему репо **до 300 MB** (планка поднята решением пользователя 2026-08-02; исходные 200 MB перейдены ещё 2026-07-08 — бинари по делу: вендоренный Three, фото 41/42, обложки 38). При приближении к 300 — сначала `git gc`, потом разговор о выносе тяжёлого; историю не переписываем.
- Если приближаемся к 500 MB — пересмотрим стратегию, перейдём на Git LFS для тяжёлых типов.

### Кросс-вариантное использование

Все варианты одного МТК (например `mtk42-archive/` и `mtk42-pendulum/`) тянут из одного `assets/mtk42/...`. Не дублируй файлы между вариантами.

Пути из вариантов: `../assets/mtkXX/<...>` (относительно своего варианта).

### Что нельзя

- Бинарные ассеты **вне `assets/`** (например `mtk42-archive/portraits/...`) — будут отброшены `.gitignore`. Перенеси в `assets/mtk42/portraits/`.
- Огромные файлы (>50 MB одиночный) — сначала согласуй с координатором.
- Кросс-МТК ассеты в чужом `assets/mtkYY/` — если нужно шарить между МТК, кладём в `assets/shared/` через координатора.

## Git-стратегия

- Каждая сессия коммитит **только в свою feature-ветку** `claude/<имя>`.
- Не коммитить напрямую в `main` без согласования.
- Merge в `main` — через merge commit; синхронизация назад через `git fetch && git merge main`.
- Из-за файловых границ выше — конфликтов при merge почти не будет. Если конфликт по README/index.html — это значит чужой регион случайно задет; откатить.

### Кто делает merge

**Координатор** (правило от 2026-08-02; отменяет прежнее «сессия сама» — см. историческую заметку ниже).

Твой flow как сессии:
1. Коммитишь в свою ветку `claude/<имя>` — сколько угодно, это черновики.
2. Готовый смысловой кусок → говоришь пользователю **«готово к merge»**.
3. Координатор проверяет скоуп → мержит в main → сам обновляет хаб/лендинг (карточки, HUB_VARIANTS) → по команде пользователя деплоит.
4. После его merge делаешь `git merge main` — забираешь общий свежак.

Почему через координатора: он проверяет скоуп **до** попадания в main (а не постфактум), синхронно с merge обновляет хаб/лендинг (иначе новые прототипы висят вне карусели), и держит единственную линию на деплой.

**VPS (`ssh ostrov`, `/var/www/bmk-3842`, docker) — только координатор.** Любые операции, включая чтение. Push в origin — только координатор и только по явной команде пользователя.

*Историческая заметка:* до 2026-08-02 здесь стояло «сессия мержит сама после одобрения пользователя» — merges сессии 39 от 2026-08-01/02 (картотека, иллюстрации, «Не на карте») сделаны **по действовавшему тогда правилу**, претензий к ним нет; скоуп проверен координатором постфактум, всё чисто.

### Связь между сессиями (два канала, с 2026-08-03)

**Канал 1 — md в репо (большое и долгоживущее):** правила, стандарты, задачи, заявки с историей — COORDINATION (Хронология), PLAN-KIOSK, README. Всё, что должно пережить сессию и быть найденным позже, — только сюда.

**Канал 2 — межсессионные сообщения (малая коммуникация):** вопросы, «готово к merge», короткие заявки, уточнения — `mcp__ccd_session_mgmt__send_message` (адресат — из `list_sessions`). Сообщение приходит с пометкой «From <сессия>». Координатору можно писать напрямую этим каналом; координатор рассылает сессиям тоже им (с одобрения пользователя на каждое сообщение). Пользователя дёргать только там, где нужно его решение.

Файлы в чужие worktree (`SERVER-NOTE.md` и т.п.) по-прежнему пишет только координатор — сессиям нельзя.

## Тач-стандарт киоска (2026-08-02, ОБЯЗАТЕЛЬНЫЙ для всех МТК)

Мы делаем **не сайт, а тач-интерфейс музейного киоска** (49″ 3840×2160, палец ≈ 15 мм ≈ 53 px, посетитель любого возраста). Решение пользователя от 2026-08-02. Общий кит: `assets/shared/kiosk/` (зона координатора) — `kiosk.css` (переменные + утилиты) и `hint.js` (`KioskHint` — призыв к жесту). Числа ниже канонические; в прототипах использовать переменные кита, не хардкод.

1. **Тач-таргеты.** Любой интерактив ≥ **64×64 px** (`--touch-min`), основные контролы (навигация, режимы, фильтры) — **96×96** (`--touch-primary`), зазор между соседними ≥ **16 px**. Хабные угловые стрелки (88 px) — эталон масштаба.
2. **Отступ от кромки.** Интерактив не ближе **64 px** к краю панели (`--edge-safe`), от нижней кромки — **80 px** (`--edge-safe-bottom`): рамка + ладонь. Чипы/легенды, прижатые к краю, — отодвинуть.
3. **Видимый скролл.** Везде, где контент скроллится, полоса прокрутки **видна всегда** (не auto-hide): класс `.kiosk-scroll` из кита (18 px, латунь на полупрозрачном треке). Скрытых скроллов быть не должно — посетитель не догадается.
4. **Призыв к жесту.** Где есть зум — подсказка «щипок» (`KioskHint.attach(el, {gesture:"pinch"})`), где драг/пан — `"drag"`, где свайп — `"swipe"`. Поведение единое: видна при простое, гаснет по первому касанию, возвращается через 30 с бездействия. Свои самодельные подсказки заменить на кит.
5. **Кегли.** Подписи/легенды ≥ **24 px** на 3840 (`--type-min-label`), текст на кнопках/чипах ≥ **32 px** (`--type-min-ui`). (Ужесточение нормы 4K-смоука от 2026-07-22.)
6. **Карты — только вектор.** Плоские карты всех МТК: векторная подложка `data/ne_110m_countries.geojson` + канон `MtkProjection.WinkelTripel` (`assets/shared/lib/projection.js`). Фото/растровые подложки на плоских картах убрать. **Исключение: сферические глобусы** (38-globe/v3-globe, 39-world/globe) — там текстуры допустимы.
7. **Унификация управления.** Однотипные контролы — одинаковые по виду/месту во всех МТК: размеры и скролл из кита, палитра из брендбука (COORDINATION → «Шрифтово-цветовые правила»), фильтры-чипы и легенды — в безопасной зоне, не по углам впритык.

Порядок: каждая сессия проходит свои прототипы чек-листом 1–7 в ближайшую итерацию, коммитит, «готово к merge». Координатор после правок прогоняет **тач-аудит** (скрин-проход + проверка отступов/скроллов/хинтов) и сводит результат здесь же.

## Киоск-стандарт v2 (2026-08-02) — платформенные требования

Продолжение тач-стандарта (пункты 1–7 выше действуют). Архитектура и фазы — **[PLAN-KIOSK.md](PLAN-KIOSK.md)** (канон). Кратко, что обязано уметь КАЖДОЕ приложение МТК:

8. **Единое приложение, сцены вместо страниц.** МТК собирается в `mtkXX-app/`: все варианты — сцены одной страницы с контрактом `mount/unmount/pause/resume/reset/setLang/setA11y` (см. PLAN-KIOSK). Переключение сцен — кроссфейд без перезагрузки и дёргания; ассеты преролятся один раз на старте. Ядро — `assets/shared/kiosk/kiosk-core.js` (зона координатора, фаза 0).
9. **Standby-режим.** При простое `T_standby` (настраиваемо, деф. 180 с) — аттрактор-заставка из собственного материала МТК + «Коснитесь экрана»; FPS в standby ≤ 10; касание возвращает на дефолтную сцену в дефолтном состоянии.
10. **Idle-сброс.** При простое `T_reset` (настраиваемо, деф. 90 с) — сцены сбрасывают отбор/зум/карточки, язык возвращается на RU. Оба таймера — из `kiosk.config.json` + сервис-панели. **Открытые карточки/модалки/оверлеи таймер НЕ замораживают** — idle-сброс их закрывает (ушедший посетитель не должен оставлять киоск в своём состоянии); `suspendIdle` — только для сервис-панели (подтверждено координатором 2026-08-03, прецеденты 42 и 39).
11. **Языки RU/EN/ZH.** Все UI-строки — через словари `mtkXX-app/i18n/*.json` (хардкод запрещён); переключатель — компонент рантайма; ZH — сабсет Noto Sans SC (вендорить). Контентные переводы — отдельная ветка с куратором (схема данных: поля `{ru,en?,zh?}` с фолбэком).
12. **Режим слабовидящих.** Кнопка рантайма: типографика ×1.5, контраст-тема без полупрозрачностей, приглушённые анимации, таргеты ×1.25; сцены дополнительно упрощают плотность в `setA11y()`. Сброс по idle.
13. **Настройки — внутри МТК, не в хабе.** Позиция/яркость/размер кнопок навигации, косая подложка, тайминги, дефолтные язык/сцена — сервис-панель приложения (гейт `?service=1`/тройной тап), хранение `localStorage["mtkXX-kiosk"]` поверх `kiosk.config.json`. Хабные стрелки/⚙/полосы после миграции всех МТК удаляются, хаб остаётся лаунчером. **Плюс (v1.2, решение пользователя 2026-08-02): настройки СЦЕН — там же.** Сцена декларирует свои параметры схемой `settings:[{key,label,type,min,max,step,default}]` + `applySettings(values)` (контракт в PLAN-KIOSK) — ядро рисует их в сервис-панели группой «Настройки МТК», хранит и сбрасывает единообразно. Тюнинг-панели старых прототипов при миграции ОБЯЗАТЕЛЬНО переезжают в эту схему (своих кастомных панелей настроек в приложениях не заводить).
14. **Перф и автономность.** Неактивная сцена: 0 rAF / 0 таймеров. Буфер ≤ 8.3 Мп, цель 60 fps. Ноль сетевых обращений в рантайме (включая `<iframe src>`, `fetch`, `Image.src`, `@import` — прецедент Sketchfab у МТК 41); watchdog + журнал ошибок в localStorage; ночной авторестарт (деф. 04:00).

Фазы: 0 ядро (координатор) → 1 пилот **МТК 42** → 2 тираж 39/40/41, затем 38 → 3 языки/a11y → 4 аудит+приёмка. До конца миграции текущая хаб-карусель работает как раньше — ничего не ломаем на ходу.
